# src/io — Non-Obvious Type Decisions

Hardware evidence for these bullets lives in the cited issues and commits, not here. Hardware questions about `io/esp_idf.rs` go to `esp32-hw-probe/`, and about `io/embassy.rs` to `embassy-hw-probe/` (each has its own `CLAUDE.md`). As with `.claude/rules/wire-framing-hardware-verification.md`, an agent doesn't self-verify on hardware: hand the probe to the user.

## ESP-IDF

- **`EspIdfTlsConnector::unverified()` disables verification through a custom `crt_bundle_attach` hook (`accept_any_certificate`), because ESP-IDF has no runtime switch for it** (#168). In v5.5.5 the only built-in skip is the build-time `CONFIG_ESP_TLS_SKIP_SERVER_CERT_VERIFY`, which depends on `CONFIG_ESP_TLS_INSECURE` (off by default). That is an app sdkconfig choice bambino can neither see nor require, and `esp_idf_svc::tls::Config` (0.53.0) has no field for it. In v5.5.5's `set_client_config`, `crt_bundle_attach` is checked before `use_global_ca_store` and `cacert_buf`, gated only by `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE` (on by default), and `MBEDTLS_SSL_VERIFY_REQUIRED` is set immediately before the hook runs, so the hook's `VERIFY_NONE` is what takes effect. Using the hook means bypassing `EspTls::negotiate`: `Config::try_into_raw` and `EspTls`'s `*mut esp_tls` are private, so `negotiate_unverified_step` calls `esp_tls_conn_new_sync` through `EspTls::context_handle()` and copies `EspTls`'s private `internal_connect` return-code mapping. Re-check both on an `esp-idf-svc` upgrade. With the bundle Kconfig off, `connect()` fails fast with a `SocketError`. `with_certs` rejects an empty or wholly unparseable anchor set rather than falling back to this path (#531).
- **`EspIdfTlsConnector::connect` classifies handshake failures from `esp_tls`'s mbedTLS error record, not the `EspError`**, because every failed step reaches Rust as the same `ESP_FAIL`. `NET_CONN_RESET`/`SSL_CONN_EOF`/`PEER_CLOSE_NOTIFY` → `ConnectionReset`; `NET_RECV_FAILED`/`NET_SEND_FAILED` → `ConnectionAborted`; any `*_ALLOC_FAILED` (or `ESP_ERR_NO_MEM` in the ESP-type record) → `ResourceExhausted`; certificate rejections → `CertificateInvalid` (`query_verify_failure` first, then `account_for_trust_store`); anything else → `SocketError::Other` carrying both recorded codes. There are no DNS or dial arms: the connector adopts an already-connected socket. Post-handshake reads and writes share the classifier, `mbedtls_error_kind` in `io/mod.rs`, so Embassy uses it too and it runs on the host. **Sign trap:** ESP-IDF v5.5.5 stores every mbedTLS code in the error record *negated*, while `esp_tls_conn_read`/`write` return it un-negated. Only the record goes through `mbedtls_code_from_esp_tls_record`; feeding it raw made every handshake arm unreachable (#386), and negating the read/write path too would undo #303. Hardware results: #386.
- **`EspTlsLogQuiet` lowers the global `esp-tls` log level to `ESP_LOG_ERROR` for the length of each handshake** (#156). `connect` pins `timeout_ms` to `TLS_HANDSHAKE_STEP_BUDGET_MS` (1ms), and `esp_tls_conn_new_sync` logs `Failed to open new connection in specified timeout` at warning level on every step that doesn't finish the handshake, so a healthy 1.4s handshake used to log ~60 false failures. Keep these true if this is touched:

  1. The guard is nesting-counted: depth and saved level live in one `static` `Mutex`, because MQTT and FTPS handshake concurrently and an inner guard's drop must not un-silence the tag under an outer one.
  2. Never widen it to `ESP_LOG_NONE`: real `esp-tls` failures are `ESP_LOGE` and must still reach the consumer.
  3. `report_anchor_bundle_parse` re-runs the anchor parse at construction time, outside the suppressed window, because `set_ca_cert` tolerates a partial parse and only *warns*. A bundle that loaded four of five BBL anchors (#145) would otherwise verify some models, fail others, and look clean in the log. Its report must stay visible at the default level in both directions (#158): failures at `error`, the all-parsed confirmation at `info` (not `debug`, or its absence reads as "nothing reported"; not `warn`, since nothing is wrong).
- **`CertificateFailure::IncompleteTrustStore` replaces `UntrustedAnchor` when the failed handshake held fewer anchors than the caller supplied** (#384). The construction-time parse can disagree with the handshake's under memory pressure, because `mbedtls_x509_crt_parse` skips an anchor whose decode can't allocate. `count_handshake_anchors` reads the failed context's `private_conf->private_ca_chain`, which survives a failed handshake in v5.5.5 and has no public getter (re-check both on an ESP-IDF/mbedTLS bump), and counts nodes with `version != 0`. The baseline is the DER count supplied, **not** the construction-time count, by decision: otherwise both parses running short would still report `UntrustedAnchor`. Accepted consequence: a permanently malformed anchor disables the TOFU prompt until fixed. Embassy can't see its trust store and never produces this.
- **`EspIdfUdpSocket::recv_from` sleeps `UDP_RECV_POLL_INTERVAL` (15ms) on `WouldBlock` before returning `TimedOut`.** Without it, callers that loop on it, like `discover_devices`, spin at 100% CPU for the whole discovery window.
- **`TLS_POLL_INTERVAL` (20ms) looked like pacing, not cost, in #160's measurement**: a 5ms interval changed total polling time by 0.4% (see `reference/01_network_discovery.md`, "Where the handshake time actually goes"). That run predates `bacf200` (#294), which bounds each `esp_tls_conn_new_sync` step to `TLS_HANDSHAKE_STEP_BUDGET_MS`. Re-measure before using it to rule out a change to the interval, or the readiness path described on the constant.
- **A `PrinterClient` with all three channels overflows ESP-IDF's default 8KB main task, and the cause is the connect futures, not the client struct.** Measured on an ESP32-C6: the client is ~1.6KB, the sequential `connect_*` futures peak at ~4.8KB, and `connect_all` at ~20KB, because `join3` keeps all three handshakes and their timeout races alive at once. Connecting sequentially overflows the 8KB task too, so `connect_all` is not the cause. Figures are in commit `6a34f3f`, whose `esp32-hw-probe/src/main.rs` has the `size_of` logging that produced them; restore it to re-measure. A builder-style construction API won't help: unconfigured channels are zero-sized `Dummy` types. Run the client on a thread with a bigger stack (`std::thread::Builder::stack_size`, as `esp32-hw-probe/sdkconfig.defaults` notes) or raise `CONFIG_ESP_MAIN_TASK_STACK_SIZE`. On Embassy, where task stacks are sized up front, `connect_all`'s ~4x stack is its real cost.
- **`esp-idf` verification needs `scripts/check-esp-idf.sh [chip]` (default `esp32c6`), not plain `cargo check`.** The target needs Python/cmake/ninja/the ESP-IDF SDK, `rust-src`, and for Xtensa a forked toolchain. The script runs in the `espressif/idf-rust:<chip>_latest` Docker image and caches the registry, `rust-src` and `target/` in named volumes. It runs `cargo clippy`, and it is the **only** lint gate for `cfg(feature = "esp-idf")` code, since `make check-fast` never compiles it. CI (`.github/workflows/esp-idf.yml`) runs it on any push touching `src/**`, `build.rs`, `Cargo.toml`/`Cargo.lock`, `Makefile` or the script, because esp-idf code also lives in `io/mod.rs` and `mqtt/client/`. Run it yourself before pushing a change here: CI only reports after the push lands. Neither gate passes `-D warnings`, because both toolchains float (`dtolnay/rust-toolchain@stable`, the image's `latest` tag) and a routine clippy release would turn `main` red on untouched code; pinning both is the prerequisite for a hard gate. There is no `esp32p4` image tag yet, and the Xtensa tags (`esp32`/`s2`/`s3`) are untested with this script.

## Embassy

- **Embassy's TLS backend is `mbedtls-rs`**, giving real TLS 1.2+1.3 and hardware crypto. `EmbassyTlsConnector<'a>` holds a `TlsReference<'a>` into one process-wide `Tls`, because MbedTLS permits only one instance. `negotiated_version()` returning `None` means "handshake not complete or session closed", not "can't tell": `mbedtls-rs` gates the accessor on its own `connected` flag, because MbedTLS seeds the underlying field with the *configured maximum*. `connect()` sets only `min_version`, deliberately not `max_version`: no affected model is known to offer 1.3, and #196 (closed) left the right scope for such a knob undecided. Against a peer that insists on 1.3, the FTPS `allow_unverified_tls_1_2` bypass (`src/ftps/CLAUDE.md`) is the only way through. Hardware results: #292.
- **Every embassy dial goes through `EmbassySocketPool`, which never removes a socket, because embassy-net can't otherwise close a connection with a FIN.** embassy-net 0.9.1's `TcpSocket::drop` removes the socket from the stack before the queued FIN is sent, and its `TcpClient` drops sockets exactly that way. The pool's states (`Closed`/`TimeWait` as the only free states, draining, the RST only after `DRAIN_BOUND_MS`, the pool task) are explained in commit `1aaf503`. `tests/embassy_socket_teardown_test.rs` guards the FIN on the host, but only `embassy-hw-probe` shows how the printer reacts. Re-run it after any embassy-net or smoltcp change (see the warning above `embassy-net` in `Cargo.toml`, and the probe's README).
- **Teardown calls `TlsConnector::close` and then drops the stream** (#293; the rule for every backend is `.claude/rules/tls-session-teardown.md`). On embassy a session sends close_notify only on `close` and frees its memory only on drop. As a result, `mbedtls-rs`'s "Session dropped without being closed properly" warning fires only for a stream dropped without `close`, which keeps it useful as a signal. Session memory and the two-sessions-not-three limit on a C6 are in the `mbedtls-rs` comment in the root `Cargo.toml`.

## All backends

- **`SocketError::Other` is `Cow<'static, str>`, not `&'static str`**, the same no_std/alloc pattern as `Error::ProtocolViolation`, so ESP-IDF's mapping can attach the real `EspError`. As a result `SocketError` is not `Copy`.
- **`TlsConnector::peer_chain_der` returns the peer's DER chain, leaf first, on tokio and ESP-IDF, and `None` on embassy** (#142). It lets a consumer pin a printer cert without this crate owning storage or TOFU policy. `None` means "this platform can't report it", never "the peer sent nothing" or "skip validation", so a caller enforcing a pin must fail closed on it. Embassy's gap is real: `mbedtls-rs` exposes neither a peer-cert accessor nor the raw `mbedtls_ssl_context`. ESP-IDF needs `CONFIG_MBEDTLS_SSL_KEEP_PEER_CERTIFICATE`; it's on by default, but pin it explicitly, or the cert is freed at the end of the handshake and the accessor degrades to `None`. ESP-IDF copies the DER out because the live SSL context owns the chain. Only a P1S's chain has been checked (`reference/01_network_discovery.md`); for another model run `bambino-cli inspect-cert`, which goes through `TokioTlsConnector` + `peer_chain_der`, the real consumer path.
- **Every socket-creating backend disables Nagle, and they must stay in step**: `EspIdfTcpStream::connect` calls `set_tcp_nodelay(true)` (socket2's name), `TokioRawStreamFactory::dial` calls `set_nodelay(true)`, and `EmbassyRawStreamFactory::dial` calls `set_nagle_enabled(false)` on the socket it leases. The first two warn and continue on failure (`warn_nodelay_failed`) rather than propagate, unlike the adjacent `set_nonblocking`, which is a correctness requirement. Nagle-off is a latency setting, and if host and device differ on it, every host-vs-device timing comparison misleads (#160). The embassy call is infallible.
- **`SocketError::ResourceExhausted` sources** (#385):
  - **std backends:** `ENOMEM`, through the two shared mappers (`map_std_io_error`, `map_embedded_io_error_kind`). `ENOBUFS`/`EMFILE`/`ENFILE` stay `Other` by decision, since catching them needs `libc` as a direct dependency.
  - **ESP-IDF adds:** mbedTLS `*_ALLOC_FAILED` codes (both halves of a composite code), `ESP_ERR_NO_MEM` from the ESP-type record, `EspTls::adopt`, `EspIdfTimer::new` (`esp_setup_error`), `EspIdfTimer::sleep` re-allocating a timer a cancelled sleep lost (`TimerError::ResourceExhausted`, via `timer_failure_error`/`deadline_error` and the polling loops, #390), and `ESP_ERR_NO_MEM` returned by `esp_mbedtls_read` as a byte count (`esp_tls_read_count`, #387).
  - **Embassy adds:** the same mbedTLS codes, which is why `EmbassyTlsConnector::Stream` is the `EmbassyTlsStream` wrapper, not `mbedtls_rs::Session`: `Session`'s `embedded_io::Error` impl flattens every code to `ErrorKind::Other`. `EmbassyRawStreamFactory::dial` also reports it when every pool socket is leased, which is a full pool rather than low memory, but the same "local, clears once something is released" condition.

  **A path that formats its own `SocketError::Other` from an `io::Error` bypasses the shared mappers and must check `OutOfMemory` itself** (`poll_connect_revents` didn't). A stream read or write failure reaches `ResourceExhausted` only if the call site passes the error's kind through `map_embedded_io_error_kind`; mapping every failure to one fixed variant reports out-of-memory as a dropped link (#389). A failed Rust heap allocation aborts and never produces it. ESP-IDF's hardware-AES DMA path returns a bare `-1` on allocation failure, which arrives as mbedTLS's catch-all `-0x0001` and is deliberately left as `Other`. Sweep results: #385.
- **`SocketError::CertificateInvalid(CertificateFailure)` is populated by all three backends, and the mbedTLS half of the mapping lives in `io/mod.rs`** (#157). ESP-IDF (`query_verify_failure`, via `esp_tls_get_ssl_context` → `mbedtls_ssl_get_verify_result`) and Embassy (`Session::tls_verification_details`) share `map_mbedtls_verify_flags` and the `mbedtls_badcert` constants. The constants are redeclared rather than imported from either `-sys` crate so one mapping serves both platforms and is unit-testable on the host. If this is touched:

  1. `map_mbedtls_verify_flags` returns `None` for `0`, `u32::MAX`, and a bare `SKIP_VERIFY` (passed, never ran, deliberately skipped), and every caller then keeps the error it already had, never fabricating a cause. `SKIP_VERIFY` is masked off rather than short-circuited, so real flags beside it still report.
  2. mbedTLS sets *every* applicable flag, so the if-chain order is a documented precedence: missing → algorithm → purpose → revoked → expired → future → untrusted → name mismatch. `UntrustedAnchor` is the only verdict for which offering trust-on-first-use capture is correct, so mis-ordering it is a security change. `InvalidPurpose` sits above it so a cert barred from server auth never opens a capture prompt. Hardware confirmed that mbedTLS sets both flags on an untrusted, wrongly named chain and that the order picks `UntrustedAnchor` (#157).
  3. An unrecognized flag maps to `Unspecified`, never `None`: the certificate was still rejected.

  Two absences are deliberate. There's no "revocation status unknown" verdict: `BADCRL_*` and rustls's `UnknownRevocationStatus` degrade to `Unspecified`, since this crate does no CRL/OCSP and Bambu certs carry no CRL distribution points. And `UntrustedAnchor` is broader than "self-signed": `check_ca_capable` (`io/tokio/cert_verify.rs`) also reports a non-CA-capable intermediate as `UnknownIssuer`, so a consumer must not read that verdict as "a benign printer certificate". On the rustls side, `map_tls_handshake_error` (`io/tokio.rs`) downcasts the boxed `rustls::Error` out of tokio-rustls's `io::Error`; without that downcast the typed verdict survives only in a display string. `NoCertificatesPresented` sits at the top level of `rustls::Error`, not under `CertificateError`, so it is matched separately, and that arm is easy to drop in a refactor.
