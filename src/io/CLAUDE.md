# src/io — Non-Obvious Type Decisions

- **`EspIdfTlsConnector`'s anchor-less path (`new()`/`with_certs` with an empty CA set) disables certificate verification via a custom `crt_bundle_attach` hook, not ESP-IDF's `skip_server_cert_verify` flag.** `esp_idf_svc::tls::Config` (0.52.1) has no field for that flag, and the flag itself only exists in the generated `esp_tls_cfg` at all when the consuming app's sdkconfig sets `CONFIG_ESP_TLS_INSECURE` (off by ESP-IDF default) — a build-time condition bambino cannot see or require. `crt_bundle_attach` has neither limitation: confirmed against ESP-IDF v5.2.3's `esp_tls_mbedtls.c` `set_client_config`, it's checked *before* `cacert_buf`/`use_global_ca_store`/`skip_server_cert_verify`, gated only by `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE` (on by ESP-IDF default), and `set_client_config` sets `MBEDTLS_SSL_VERIFY_REQUIRED` immediately *before* invoking the hook — so `build_unverified_tls_cfg`'s hook (`accept_any_certificate`) overriding it back to `MBEDTLS_SSL_VERIFY_NONE` via `mbedtls_ssl_conf_authmode` is what actually takes effect, and is exactly what that flag documents (peer cert never checked). This bypasses `esp_idf_svc::tls::EspTls::negotiate`/`Config` entirely for this one case: `Config::try_into_raw` and `EspTls`'s internal `*mut esp_tls` field are both private, so `negotiate_unverified_step` calls `esp_tls_conn_new_sync` directly via the one public seam `EspTls::context_handle()` exposes, mirroring `EspTls`'s own private `internal_connect`'s exact return-code mapping — re-verify both stay in sync if `esp-idf-svc` is upgraded. If `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE` is disabled, `connect()` fails fast with a clear `SocketError` instead of reaching this path at all (the field wouldn't even exist on that build's `esp_tls_cfg`). **Confirmed on a real ESP32-C6 against a live P1S** (`esp32-hw-probe`): the unverified handshake completed (TLS 1.2) and `peer_chain_der` returned both chain certificates (743 + 873 DER bytes, leaf then the `BBL CA` root) — the crt_bundle_attach hook works end to end and the TOFU-capture use case it exists for is reachable. GitHub issue #168.
- **`EspIdfTlsConnector::connect` maps handshake failures to distinct `SocketError` variants** instead of collapsing to `ConnectionRefused`: DNS/address failures → `AddressNotAvailable`, genuine refusals → `ConnectionRefused`, timeouts → `TimedOut`, opaque fallback → `SocketError::Other` (carries the formatted `EspError`).
- **`SocketError::Other` is `Cow<'static, str>`, not `&'static str`** (same no_std/alloc pattern as `Error::ProtocolViolation`) — `SocketError` is no longer `Copy` as a result. Lets ESP-IDF's error mapping attach the real `EspError` instead of a fixed string.
- **`TlsConnector::connect` dropped its unused `port: u16` parameter** (breaking, pre-1.0) — the raw stream handed in is already connected to its target port via `RawStreamFactory::dial()`. Test mocks that faked port-dependent behavior now track call count via `AtomicBool` instead.
- **`EspIdfUdpSocket` no longer busy-spins on `recv_from`** — sleeps `UDP_RECV_POLL_INTERVAL` (15ms) on `WouldBlock` before returning `TimedOut`, matching `TokioUdpSocket`'s pacing. Without this, tight-loop callers like `discover_devices` burned 100% CPU for the full discovery window.
- **Embassy's TLS backend is `mbedtls-rs`, not `embedded-tls`** (breaking, pre-1.0) — real TLS 1.2+1.3 and hardware crypto. `EmbassyTlsConnector<'a>` holds a `mbedtls_rs::TlsReference<'a>` into a single process-wide `Tls` instance (MbedTLS permits only one). `negotiated_version()` reports the real version via `mbedtls-rs` 0.3's `Session::tls_version()` (GitHub issue #289) — `None` there means "handshake not complete / session closed", not "this backend can't tell", because the accessor is gated on `mbedtls-rs`'s own `connected` flag (MbedTLS seeds the underlying field with the *configured maximum* at setup and on every reset). So `require_tls_1_2_if_enforced` now passes on P2S/X2D whenever the printer negotiates 1.2 of its own accord, which the bambuddy nine-unit probe says it does. `connect()` still sets only `min_version`, so the connector cannot *cap* the peer at 1.2 even though `ClientSessionConfig::max_version` exists in 0.3 — deliberately not wired up, since neither affected model is known to offer 1.3 and the right scoping for such a knob is the open question in closed issue #196; against a peer that did insist on 1.3 the FTPS `allow_unverified_tls_1_2` escape hatch is still the only way through. **Confirmed on an ESP32-C6 (bare metal, esp-hal 1.1 + esp-radio 0.18 + embassy-net 0.9) against a live P1S** via `embassy-hw-probe/`, first run, all stages green: the handshake completed and `negotiated_version` reported `Some(Tls12)` — so the #289 accessor is right on hardware, not just against the host's loopback rustls server. One `Tls` instance shared by four connectors across the run (MQTT, FTPS control, FTPS data, plus a bare probe session) held up, which is the case the `TlsReference` design exists for. Software crypto: the probe leaves `mbedtls-rs`'s chip feature off (see its `Cargo.toml` for why), so this says nothing about accelerated-handshake timing.
- **`TlsConnector::peer_chain_der` is implemented on tokio and ESP-IDF, `None` on embassy** — a post-handshake inspector (same defaulted-method shape as `negotiated_version`) returning the peer's DER chain leaf-first, so a consumer can pin a printer cert without this crate owning any storage or TOFU policy. `None` means "this platform can't report it", never "the peer sent nothing" and never "skip validation" — a caller enforcing a pin must fail closed on it. Embassy returns `None` honestly — unlike `negotiated_version`, which 0.3 did fix, this gap is real: `mbedtls-rs` exposes neither a peer-cert accessor nor the raw `mbedtls_ssl_context` pointer (its only post-handshake inspectors are `tls_verification_details`/`tls_alpn`), so unlike ESP-IDF — which gets there via `esp_tls_get_ssl_context` — there's nothing to call `mbedtls_ssl_get_peer_cert` on. The ESP-IDF path needs `CONFIG_MBEDTLS_SSL_KEEP_PEER_CERTIFICATE` (on by ESP-IDF default; pin it explicitly rather than inherit it, or the cert is freed at end of handshake and the accessor degrades to `None`), and copies the DER out because the chain is owned by the live SSL context. **Confirmed on a P1S: the printer sends two certificates** — the `CN=<serial>` leaf (no extensions at all, i.e. X.509 v1, which is the same reason `CnFallbackServerVerifier` exists) followed by the self-signed `CN=BBL CA` root, `CA:TRUE`, byte-identical to the known BBL CA root. So an anchor *can* be captured at first contact and fed back through `with_certs(..)` for real `VERIFY_REQUIRED` on every later connection — a consumer is not limited to comparing a leaf fingerprint with verification off. Only the P1S has been checked; run `bambino-cli inspect-cert` against any other model rather than assuming it generalizes. That command goes through `TokioTlsConnector` + `peer_chain_der` (not a bespoke verifier), so it exercises the real consumer path and can't drift from it. See GitHub issue #142.
- **Both socket-creating backends disable Nagle, and must stay in step** — `EspIdfTcpStream::connect` and `TokioRawStreamFactory::dial` each `set_nodelay(true)`; embassy is exempt because the caller supplies the stream and this crate never creates that socket. Failure warns and continues rather than propagating, unlike the adjacent `set_nonblocking` (a correctness requirement, since the poll loops retry on `WouldBlock`) — Nagle-off is a latency optimisation and shouldn't fail a connection that would otherwise work. Keep the two backends matched: a latency characteristic present on the printer but not the host makes every host-vs-device timing comparison misleading, which is precisely what GitHub issue #160's measurements turned on. Measured context for why this matters (ESP32-C6 against a P1S, TLS 1.2, ECDHE-RSA-AES256-GCM-SHA384): a 1415ms handshake is ~790ms waiting on the printer, ~435ms local mbedTLS compute, and ~190ms residual — the peer figure being independently established by timing the same handshake from a laptop on the same LAN (805ms ±2%), which is the control that stops "the loop is slow" from being read into a peer that is simply slow for every client.
- **`TLS_POLL_INTERVAL` is not a latency knob, and the measurement to prove it is already done** — quadrupling the poll rate (20ms → 5ms) moved total polling time by 0.4% (1004.8ms → 1008.9ms) while step count scaled 3.94x, on 8 runs each. Every sleep follows a genuine "peer has not answered", so the loop paces rather than costs; 5ms was marginally *worse* (~150 extra `esp_tls_low_level_conn` calls at ~0.14ms of per-call overhead). Don't re-litigate the interval, and don't build the `async-io`/`MountedEventfs` readiness path its doc comment describes on latency grounds — the recoverable quantisation is bounded by (wait episodes × interval/2), which this data caps well below the ~190ms residual. The handshake loop's own summary line reports steps, the two sums, and the slowest single step, so a future regression here is measurable without new instrumentation.
- **`esp-idf` target verification needs `scripts/check-esp-idf.sh [chip]` (default `esp32c6`), not plain `cargo check`** — the target needs Python/cmake/ninja/the ESP-IDF SDK, `rust-src`, and for Xtensa a forked toolchain, none of which plain `cargo check` provides. The script pulls the matching `espressif/idf-rust` Docker image and caches the registry/`rust-src`/`target/` across runs via named volumes. Wired into CI via `.github/workflows/esp-idf.yml`, but path-filtered to `src/io/esp_idf.rs`/`scripts/check-esp-idf.sh`/`Cargo.toml` — run it yourself when touching this file rather than relying on CI to catch it on an unrelated push. There's no `esp32p4` Docker tag yet (spike before relying on `IDF_TARGET=esp32p4` against the `esp32c6` image); Xtensa tags (`esp32`/`s2`/`s3`) are also unverified by this script so far. It runs `cargo clippy`, not `cargo check` — `make check-fast`'s clippy never compiles anything behind `#[cfg(feature = "esp-idf")]`, so this script is the *only* lint gate for this file. Neither gate passes `-D warnings`: both toolchains float (CI's `dtolnay/rust-toolchain@stable`, the image's `:latest` tag), so denying warnings would turn a routine clippy release into a red `main` on untouched code. Fix warnings when they appear instead; pinning both toolchains is the prerequisite for ever making this a hard gate.
- **Real-hardware questions about this file** (resource exhaustion, timing, anything `scripts/check-esp-idf.sh`'s static check can't observe) have a reusable flashable test harness at `esp32-hw-probe/` (own `CLAUDE.md` — reuse convention, chip retargeting, flash/run instructions). Excluded from the published crate via root `Cargo.toml`'s `exclude` entry. Built for BUG-051 (confirmed non-issue via 10,000-iteration `EspTimerService` allocation stress test on both ESP32-C6 and ESP32-C3); reused for GitHub issue #65, which confirmed on an ESP32-C3 that two `EspIdfTimer::sleep`s racing on one shared timer both complete concurrently (300ms for a pair of 300ms sleeps, not 600ms), survive 500 racing pairs without leaking `esp_timer` slots, and leave the timer usable after one is dropped mid-await. Swap its `src/main.rs` body for the next investigation rather than building new scaffolding from scratch; it takes a path dependency on `bambino` itself so a probe exercises the shipped type, not a copy of it. Same "don't self-verify, hand off to the user" rule as `.claude/rules/wire-framing-hardware-verification.md` applies here too, even though this isn't a wire-framing change.
- **Real-hardware questions about `io/embassy.rs` have their own harness at `embassy-hw-probe/`** (own `CLAUDE.md`/`README.md`), and it is a *separate package* from `esp32-hw-probe/`, not a retarget of it — esp-idf is std on `riscv32imac-esp-espidf`, embassy is no_std on `riscv32imac-unknown-none-elf` with its own stack (esp-hal + esp-radio + embassy-net), so the two have mutually exclusive feature sets and cannot share a `Cargo.toml`. The same ESP32-C6 runs both. It stages Wi-Fi/DHCP bring-up, a raw dial, a real TLS handshake with `negotiated_version`, MQTT plus one telemetry event, FTPS plus one `list_directory`, and `EmbassyTimer` monotonicity — in that order, because most of the work happens before any bambino code executes and the stage number is what says whether the crate under test was reached. Build gate: `make check-embassy-probe` (no Docker, no SDK; a `build` not a `check`, because MbedTLS needs a `memchr` the bare-metal sysroot lacks and that only fails at link time). Hardware crypto is off there — `mbedtls-rs`'s chip feature forces `esp-hal ~1.2`, which drags esp-radio onto a prerelease — so handshake timings from it are a software-crypto floor and are **not** comparable to the accelerated ESP-IDF figures elsewhere in this file. **First run (GitHub issue #292) passed every stage against a P1S**: DHCP lease, raw dial, TLS 1.2 handshake, MQTT connect + a decoded `push_status` report, FTPS connect + 90 entries from `/`, and a 500ms `EmbassyTimer::sleep` measuring exactly 500ms. Two things that run taught the probe itself, both since fixed: heap sampled only at stage *entry* reads ~50 KB at every boundary because sessions are freed before the next banner — the multi-session peak needs `esp-alloc`'s `internal-heap-stats` `Max usage` plus an exit sample, not more boundary samples; and dropping clients instead of calling `disconnect_mqtt`/`FtpsClient::disconnect` made `mbedtls-rs`'s "Session dropped without being closed properly" warning fire after every stage, which made it useless as a signal. A bare `Session` from `TlsConnector::connect` has no close method, so that warning is *correct* for a raw connector test and only there.
- **`EspIdfTlsConnector::connect` mutates a global ESP-IDF log level for the duration of the handshake** — `EspTlsLogQuiet` lowers the `esp-tls` tag to `ESP_LOG_ERROR` around the negotiate loop, because `timeout_ms = 0` makes `esp_tls_conn_new_sync` log `Failed to open new connection in specified timeout` at warning level on *every* step, so a healthy 1.4s handshake emitted ~60 lines each claiming a failure that never happened (GitHub issue #156). Two things make that safe and must stay true if this is touched: the level is nesting-counted via a `static` depth (MQTT and FTPS handshake concurrently on separate tasks, and an inner guard's drop must not un-silence the tag under an outer one), and `report_anchor_bundle_parse` runs the same `mbedtls_x509_crt_parse` at *construction* time so the partial-trust-store signal lands outside the suppressed window. That report is visible at the default log level in *both* directions and must stay that way (GitHub issue #158): failures log at `error`, and the all-anchors-parsed confirmation at `info` — not `debug`, or a consumer running at the default level can't distinguish a complete trust store from one nothing was reported about, which is exactly what happened downstream on an ESP32-P4 where the line's absence was misread as the pre-parse having been skipped. Not `warn` for the success arm either: nothing is wrong when it fires. It costs one line per `EspIdfTlsConnector::with_certs`, not per handshake. Never widen the suppression to `ESP_LOG_NONE` or drop that pre-parse: ESP-IDF's `set_ca_cert` tolerates a partial parse and only *warns*, so with both gone a bundle that loaded four of five BBL anchors (GitHub issue #145) would verify some printer models, fail others, and look identical to a clean handshake in the log.
- **A `PrinterClient` with all three channels needs more stack than ESP-IDF's default main task** — measured on an ESP32-C6: building and connecting an MQTT+FTPS+camera client in the 8KB main task overflowed it by more than 14KB and hit a stack-protection panic. **It is the connect futures, not the client struct** — measured on an ESP32-C6, after the builder chain (`with_ftps`/`with_camera` each consume the client and return a differently-typed one by value) was wrongly assumed to be the cause. Client 1640 bytes; futures `connect_mqtt` 2672, `connect_ftps` 4808, `connect_camera` 2512, **`connect_all` 20296**. So don't reach for a builder-style construction API to fix a stack problem — that hypothesis is dead, and the intermediate clients are smaller than the final one anyway since unconfigured channels are zero-sized `Dummy` types. **`connect_all()`'s stack cost is its real tradeoff**: `join3` keeps all three handshakes plus a timeout race each alive at once, so it peaks ~4.2x the sequential path (which only ever holds one future, ~4.8KB) in exchange for ~1.25-1.4s. That is a live consideration on Embassy, where task stacks are sized up front — the time is free, the stack is not. `esp32-hw-probe` logs `size_of` for the client and every connect future, so re-measure there rather than re-deriving. Run it on a thread with a bigger stack (`std::thread::Builder::new().stack_size(..)`, which is what `esp32-hw-probe/sdkconfig.defaults` recommends) or raise `CONFIG_ESP_MAIN_TASK_STACK_SIZE`. Not caused by `connect_all()` — the sequential `connect_*` path overflows identically, and the panic was first seen there.
- **`SocketError::CertificateInvalid(CertificateFailure)` is populated by all three backends, and the mbedTLS half of that mapping lives in `io/mod.rs`, not in either backend** — `map_mbedtls_verify_flags` + the `mbedtls_badcert` flag constants are shared by ESP-IDF (`query_verify_failure`, via `esp_tls_get_ssl_context` → `mbedtls_ssl_get_verify_result`) and Embassy (`Session::tls_verification_details`, the one post-handshake inspector `mbedtls-rs` *does* expose — so this backend can name why a certificate was rejected even though `peer_chain_der` stays `None`). Redeclaring the flag constants rather than importing them from either `-sys` crate is deliberate: it keeps one mapping for both platforms and makes it unit-testable on the host, where neither `-sys` crate is built. Three rules if this is touched: (1) `map_mbedtls_verify_flags` returns `None` for `0`, `u32::MAX`, and a bare `SKIP_VERIFY` (verification passed / never ran / was deliberately skipped) and every caller must then keep the error it already had — never fabricate a cause. `SKIP_VERIFY` is masked off rather than short-circuited so real flags accompanying it still report; (2) mbedTLS sets *every* applicable flag, so the if-chain order is a documented precedence (missing → algorithm → purpose → revoked → expired → future → untrusted → name mismatch), not an arbitrary match order — `UntrustedAnchor` is the only verdict for which offering trust-on-first-use capture is correct, so mis-ordering it is a security-relevant change, not a cosmetic one, and `InvalidPurpose` sits above it precisely so a cert barred from server auth never opens a capture prompt; (3) an unrecognized flag maps to `Unspecified`, never `None` — the certificate was still rejected. Two absences are deliberate, not gaps: there is no "revocation status unknown" verdict (the `BADCRL_*` family and rustls's `UnknownRevocationStatus` degrade to `Unspecified`, since this crate does no CRL/OCSP and Bambu certs carry no CRL distribution points, so such a variant could never be produced), and `UntrustedAnchor` is broader than "self-signed" — `check_ca_capable` in `io/tokio/cert_verify.rs` deliberately reports a non-CA-capable intermediate as `UnknownIssuer` too, so a consumer must not read that verdict as "a benign printer certificate". On the rustls side `NoCertificatesPresented` lives at the top level of `Error`, *not* under `CertificateError`, so `map_tls_handshake_error` matches it separately — easy to drop when refactoring that match. The rustls side is `map_tls_handshake_error` in `io/tokio.rs`, which downcasts the boxed `rustls::Error` out of tokio-rustls's `io::Error::new(InvalidData, …)`; without that downcast the typed verdict survives only inside a display string. **Confirmed on an ESP32-C6 against a P1-series printer** (four-case probe, all matched): ESP-IDF's failed SSL context *does* still hold the verify result where `connect` builds its error — withholding the printer's anchor reported `UntrustedAnchor`, a correct anchor set with a deliberately wrong TLS name reported `NameMismatch`, and those two were byte-identical `ESP_FAIL` before this change. Worth having measured rather than assumed, since `mbedtls_ssl_get_peer_cert` returns `NULL` after a failed handshake and the verify result surviving doesn't follow from the peer cert surviving. The same run confirmed the precedence against real mbedTLS: a chain both untrusted *and* wrongly named reported `UntrustedAnchor`, so mbedTLS does set both flags and the if-chain order — not just its unit tests — picks the answer. GitHub issue #157.
