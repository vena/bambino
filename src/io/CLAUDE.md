# src/io — Non-Obvious Type Decisions

- **`EspIdfTlsConnector::connect` maps handshake failures to distinct `SocketError` variants** instead of collapsing to `ConnectionRefused`: DNS/address failures → `AddressNotAvailable`, genuine refusals → `ConnectionRefused`, timeouts → `TimedOut`, opaque fallback → `SocketError::Other` (carries the formatted `EspError`).
- **`SocketError::Other` is `Cow<'static, str>`, not `&'static str`** (same no_std/alloc pattern as `Error::ProtocolViolation`) — `SocketError` is no longer `Copy` as a result. Lets ESP-IDF's error mapping attach the real `EspError` instead of a fixed string.
- **`TlsConnector::connect` dropped its unused `port: u16` parameter** (breaking, pre-1.0) — the raw stream handed in is already connected to its target port via `RawStreamFactory::dial()`. Test mocks that faked port-dependent behavior now track call count via `AtomicBool` instead.
- **`EspIdfUdpSocket` no longer busy-spins on `recv_from`** — sleeps `UDP_RECV_POLL_INTERVAL` (15ms) on `WouldBlock` before returning `TimedOut`, matching `TokioUdpSocket`'s pacing. Without this, tight-loop callers like `discover_devices` burned 100% CPU for the full discovery window.
- **Embassy's TLS backend is `mbedtls-rs`, not `embedded-tls`** (breaking, pre-1.0) — real TLS 1.2+1.3 and hardware crypto, but doesn't by itself fix P2S/X2D FTPS reliability (`mbedtls-rs` still negotiates 1.3 by default; the FTPS `allow_unverified_tls_1_2` escape hatch is what unblocks those models). `EmbassyTlsConnector<'a>` holds a `mbedtls_rs::TlsReference<'a>` into a single process-wide `Tls` instance (MbedTLS permits only one). `negotiated_version()` returns `None` honestly — the crate has no API to read it back; don't fabricate a value. Not yet verified against real Embassy hardware.
- **`esp-idf` target verification needs `scripts/check-esp-idf.sh [chip]` (default `esp32c6`), not plain `cargo check`** — the target needs Python/cmake/ninja/the ESP-IDF SDK, `rust-src`, and for Xtensa a forked toolchain, none of which plain `cargo check` provides. The script pulls the matching `espressif/idf-rust` Docker image and caches the registry/`rust-src`/`target/` across runs via named volumes. Wired into CI via `.github/workflows/esp-idf.yml`, but path-filtered to `src/io/esp_idf.rs`/`scripts/check-esp-idf.sh`/`Cargo.toml` — run it yourself when touching this file rather than relying on CI to catch it on an unrelated push. There's no `esp32p4` Docker tag yet (spike before relying on `IDF_TARGET=esp32p4` against the `esp32c6` image); Xtensa tags (`esp32`/`s2`/`s3`) are also unverified by this script so far.
- **Real-hardware questions about this file** (resource exhaustion, timing, anything `scripts/check-esp-idf.sh`'s plain `cargo check` can't observe) have a reusable flashable test harness at `esp32-hw-probe/` (own `CLAUDE.md` — reuse convention, chip retargeting, flash/run instructions). Excluded from the published crate via root `Cargo.toml`'s `exclude` entry. Built for BUG-051 (confirmed non-issue via 10,000-iteration `EspTimerService` allocation stress test on both ESP32-C6 and ESP32-C3); swap its `src/main.rs` body for the next investigation rather than building new scaffolding from scratch. Same "don't self-verify, hand off to the user" rule as `.claude/rules/wire-framing-hardware-verification.md` applies here too, even though this isn't a wire-framing change.
