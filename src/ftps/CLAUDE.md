# src/ftps — Non-Obvious Type Decisions

- **`validate_ftp_path()`** (`src/ftps/protocol.rs`, `pub(crate)`) rejects `\r`/`\n`/NUL in any path argument before it's interpolated into an FTP command line (CR/LF would let a malicious/compromised printer or MITM inject a second command). Called by every path-taking method on `FtpsClient`. `parse_unix_listing` (`src/ftps/parser.rs`) applies the same filter to parsed `FtpFile.name` values, silently skipping entries that fail it, so a filename round-tripped into another FTP command can't do the same.
- **`FtpsClient::connect` has an opt-out from its TLS-1.2-enforcement check**: `allow_unverified_tls_1_2: bool` (breaking, pre-1.0). When `true`, skips the `negotiated_version == Some(Tls12)` check entirely. Every backend can now report the negotiated version (embassy gained it with `mbedtls-rs` 0.3 — GitHub issue #289), so the check is satisfiable for real wherever the printer negotiates 1.2; this bypass is the escape hatch for a peer that insists on 1.3 on `esp-idf`/`embassy`, neither of which can cap the maximum version. Safe despite being fail-open: `upload_file`'s `SIZE` recheck and `download_file`'s acceptance of both `226` and the documented `426` close-race reply independently catch a truncated transfer regardless. `list_directory` is the weaker case and the justification does not extend to it unchanged — a listing has no `SIZE` to compare against, so its 426 tolerance is backed only by a line-framing check (a 426 whose payload doesn't end on a line terminator is rejected). A truncation landing exactly on a line boundary still passes silently there; don't cite the SIZE recheck as covering LIST. Default `false`. Only `tokio` has a real cap (`force_tls_1_2` on `build_verified_client_config_with_options`/`build_unsafe_client_config_with_options`); `esp-idf` has no upstream knob for it and `embassy` sets only `min_version`.
