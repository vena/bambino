# src/ftps — Non-Obvious Type Decisions

- **`validate_ftp_path()`** (`src/ftps/protocol.rs`, `pub(crate)`) rejects `\r`/`\n`/NUL in any path argument before it's interpolated into an FTP command line (CR/LF would let a malicious/compromised printer or MITM inject a second command). Called by every path-taking method on `BambuFtpsClient`. `parse_unix_listing` (`src/ftps/parser.rs`) applies the same filter to parsed `FtpFile.name` values, silently skipping entries that fail it, so a filename round-tripped into another FTP command can't do the same.
- **`BambuFtpsClient::connect` has an opt-out from its TLS-1.2-enforcement check**: `allow_unverified_tls_1_2: bool` (breaking, pre-1.0). When `true`, skips the `negotiated_version == Some(Tls12)` check entirely — necessary because neither `embassy`-target TLS backend can honestly satisfy that check, so without it Embassy can't talk FTPS to P2S/X2D at all. Safe despite being fail-open: `upload_file`'s `SIZE` recheck and `download_file`'s acceptance of both `226` and the documented `426` close-race reply independently catch a truncated transfer regardless. `list_directory` is the weaker case and the justification does not extend to it unchanged — a listing has no `SIZE` to compare against, so its 426 tolerance is backed only by a line-framing check (a 426 whose payload doesn't end on a line terminator is rejected). A truncation landing exactly on a line boundary still passes silently there; don't cite the SIZE recheck as covering LIST. Default `false`. Only meaningful for `embassy` — `tokio`/`esp-idf` use `force_tls_1_2` on the `TlsConnector` instead.
