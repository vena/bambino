# src/types/telemetry — Non-Obvious Type Decisions

- **Two temperature encodings, and only one is packed.** The flat fields (`bed_temper`, `nozzle_temper`, their `_target_temper` pairs) are `Option<f64>`, because the wire sends integers on H2D and floats on P1S/A1; targets always arrive separately. The composite-packed fields are `chamber_temper` (`Option<f64>`) and the `temp` of `ExtruderInfo`, `BedInfo` (`device.bed.info`, H2/P2/X2 only) and `CtcInfo`, all `Option<u32>`; values above 500 encode `(target << 16) | actual`. Read packed fields through `PrinterTelemetry::chamber_temperatures()` and the structs' `temperatures()` accessors, which apply `unpack_temperature()` themselves. Never apply `unpack_temperature()` to a flat field: an old-gen reading above 500 would decode as nonsense (guarded in `tests/bed.rs` and `tests/nozzle.rs`).
- **`DeviceTelemetry`** appears at two wire locations (see its doc comment for which triggers which). `TelemetryReport::device()` checks top-level `device` first, then `print.device` — prefer it over manually checking both.
- **`PrinterTelemetry::is_ethernet_active()`** reads `print.net.conf` bit 0 (BUG-110) — the earlier `home_flag` bit-18 heuristic was confirmed wrong (both upstreams decode that bit as prompt-sound support: BambuStudio's `m_allow_prompt_sound_detection.is_support_detect`, OrcaSlicer's `is_support_prompt_sound`). `is_ethernet_active_via_wifi_signal()` (checks `wifi_signal == "-90dBm"`) remains as a fallback for firmware that doesn't send `net.conf`.
- **Bitmask fields arrive in two shapes; decode them through the accessors, not by hand.** `AmsUnit.info` is a hex *string* (`Option<String>`, parsed by `parse_info()` via `bits::hex_u64`, which every fixed-width hex field shares); its full bit layout is in `reference/05_materials_ams.md` ("AMS Unit Info Bitmask"). `bind_switch_in` is four bits, not two (BUG-136): a 2-bit read reports a valid inlet for a unit that has none; decode it with `filament_switch_inlet()`. `ExtruderCollection.state` is an integer: extruder count in the low 4 bits, active index in bits 4–7 (`extruder_count()` / `active_extruder_index()`). `AmsTray.id` is a `String` because the wire sends `"0"`, not `0`.
- **`stg_cur`/`stg`** decode to `PrintStage` (`stage.rs`), but `stg_cur` must stay behind the [REF-MQTT-IDLEBUG] `gcode_state` gate — A1/P1 report `0` ("printing") while idle. `PrinterTelemetry::current_stage()` applies that gate and is the default; `current_stage_ungated()` is the escape hatch. Typing the value makes the gate *more* important, not less: a `PrintStage::Printing` in a UI reads as authoritative where a bare `0` did not. Idle mid-run is normal and is not completion — `stg_cur` reads idle for the tail of a run after the last queued stage ends. `stg` needs no gate. Idle is `-1` on X1 and `255` on P1; both normalize to `PrintStage::Idle`.
- **`xcam.cfg`** is an *integer* bitmask inside `print.xcam` — not the top-level `print.cfg` hex *string*. Same key name, different container, different type; do not conflate them. Its four AI detectors use a stride-3 layout with the 2-bit sensitivity field **above** each enable bit (7/10/13/16 → sensitivity at 8-9/11-12/14-15/17-18), per BambuStudio's `DevPrintOptionsParser::ParseDetectionV1_0` (`DeviceCore/DevPrintOptions.cpp`). **bambuddy places sensitivity below the enable bit** (`decode_detector` in `bambu_mqtt.py`, called as `decode_detector(5)` for spaghetti) — a pure phase difference, and BambuStudio wins here both as the authoritative source and because bambuddy's `cfg` path has no user-facing feature behind it (its AI detection is a separate Obico integration), so it is plausibly unexercised. Captures cannot arbitrate: every observed `cfg` sets all four detectors to the *same* sensitivity, decoding identically under both schemes. Don't "fix" the phase back from bambuddy.
- **`xcam` is pushall-only** — no incremental `msg: 1` frame in this repo's captures carries it, which is why `PrinterClient` caches and merges it (`last_xcam`) rather than reading `print.xcam` per frame. A `None` from `PrinterClient::xcam()` is "not seen yet", never "model lacks these settings"; `XcamTelemetry::supports_ai_monitoring()` (presence of `cfg`) answers that question.
- **`XcamTelemetry::allow_skip_parts` gates nothing.** Its semantics are unresolved: *not* a model-capability flag (Bambu documents every current model as supporting skip-objects, yet it reads `false` in every upstream fixture carrying it: twelve in ha-bambulab, one in OpenBambuAPI) and *not* a user setting (no such setting exists in Bambu Studio or on the printer). Gating `PrinterClient::skip_objects()` on it would break skip-objects outright on hardware that supports it. Resolving it needs a capture where it reads `true`.
- **`XcamTelemetry.extra`** (`#[serde(flatten)]`) is load-bearing, not decoration — this wire object is still largely uncharted and model-dependent, so unmodeled keys must round-trip. `auto_recovery_step_loss` and `filament_tangle_detect` live there deliberately: bambuddy reads them from `xcam`, but BambuStudio never does: it reads them from `home_flag` (bits 4 and 20) or from the top-level `print.cfg` string (bits 16 and 23), and no capture shows either inside `xcam`. Same for `ipcam_record`/`timelapse`, which belong to `IpcamTelemetry` from `print.ipcam`.
- **`vir_slot`** is separate from `vt_tray` — IDEX models send `vir_slot: Vec<VirtualTray>` (one per extruder), while single-nozzle models send `vt_tray: VirtualTray`. `VirtualTray` is a type alias of `AmsTray` (same wire schema), so don't reintroduce a separate struct or merge; `AmsTray.id` is `#[serde(default)]` for holders whose push omits it.
