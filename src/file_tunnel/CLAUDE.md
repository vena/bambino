# src/file_tunnel — Non-Obvious Decisions

- **Two sources, two layers** (`reference/08_file_service.md` §8.1). JSON bodies follow BambuStudio's `PrinterFileSystem`; framing follows ha-bambulab's `Tcp6000MediaSource` and open-bamboo-networking's `tunnel_local.cpp`, because Studio's framing is in a closed plugin. Details only open-bamboo-networking reports (reply/ack magics, the reject frame, upload pipelining) are treated leniently or marked "open-bamboo-networking only" in docs. Don't tighten a check on one of those without a second source.
- **A failure poisons the session; partial frames are not resumed.** Unlike the camera stream and MQTT, which keep partial-frame state across a timed-out read (`.claude/rules/wire-read-deadline.md`), this is request/reply: a read that times out or a stream abandoned mid-way leaves frames that a later request would misread. So any transport error, unparsable frame, or abandoned stream sets `poisoned`, and the only recovery is reconnecting (the same rule as `.claude/rules/ftps-poisoning.md`). A failure `result` read in full is `Error::TunnelReply` and does not poison.
- **Header and payload go out as two writes**, which is how both reference clients send them. FTPS needed the opposite (one write per command line) on a P1S; nothing comparable is known here, but a change to the write shape falls under `.claude/rules/wire-framing-hardware-verification.md`.
- **The handshake timeout is detection, not a fault bound.** A printer without the service sends nothing after the login (P1S, `01.10.00.00`, holds 60 s), so `FILE_TUNNEL_HANDSHAKE_TIMEOUT_SECS` (8 s, Studio's own fallback budget) is how a caller learns it isn't served. Under `DummyTimer` there is no timeout at all.
- **`mem:/16`'s `sequence_id` repeats the request `sequence`**, as Bambu's plugin does on the wire; Studio's skip dialog numbers its reads 1–3 instead. Either is accepted.
