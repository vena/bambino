# src/file_tunnel — Non-Obvious Decisions

- **Two sources, two layers** (`reference/08_file_service.md` §8.1). JSON bodies follow BambuStudio's `PrinterFileSystem`; framing follows ha-bambulab's `Tcp6000MediaSource` and open-bamboo-networking's `tunnel_local.cpp`, because Studio's framing is in a closed plugin. Details only open-bamboo-networking reports (reply/ack magics, the reject frame, upload pipelining), and those no capture shows (the `path` a `SUB_FILE` reply echoes, which is only logged on a mismatch), are treated leniently or marked "open-bamboo-networking only" in docs. Don't tighten a check on one of those without a second source.
- **Stopping a stream early cancels it.** A sink error, a caller's size limit, a refused `mem:/` read or an upload init whose `chunk_size`/`offset` can't be used sends `TASK_CANCEL` (Studio's `CancelRequest`) and skips the stream's in-flight frames, up to `CANCEL_MAX_SKIPPED_FRAMES`, until the cancel's reply. Poisoning is for what a cancel can't fix: a transport failure, a corrupt frame, or a cancel that gets no answer.
- **Upload writes every chunk before reading anything.** open-bamboo-networking found that a P2S answers a per-chunk read with `-9203`. Chunks go out on the init's `sequence`, and `frag_id` counts from 0. Only open-bamboo-networking reports this pipelining, and no printer here has run it, so it is the first thing to check on hardware. Don't add a per-chunk read to "be safe".
- **A failure poisons the session; partial frames are not resumed.** Unlike the camera stream and MQTT, which keep partial-frame state across a timed-out read (`.claude/rules/wire-read-deadline.md`), this is request/reply: a read that times out or a stream abandoned mid-way leaves frames that a later request would misread. So any transport error, unparsable frame, or failed cancel sets `poisoned`, and the only recovery is reconnecting (the same rule as `.claude/rules/ftps-poisoning.md`). A failure `result` read in full is `Error::TunnelReply` and does not poison.
- **Header and payload go out as two writes**, which is how both reference clients send them. FTPS needed the opposite (one write per command line) on a P1S; nothing comparable is known here, but a change to the write shape falls under `.claude/rules/wire-framing-hardware-verification.md`.
- **The handshake timeout is detection, not a fault bound.** A printer without the service sends nothing after the login (P1S, `01.10.00.00`, holds 60 s), so `FILE_TUNNEL_HANDSHAKE_TIMEOUT_SECS` (8 s, Studio's own fallback budget) is how a caller learns it isn't served. Under `DummyTimer` there is no timeout at all.
- **`mem:/16`'s `sequence_id` repeats the request `sequence`**, as Bambu's plugin does on the wire; Studio's skip dialog numbers its reads 1–3 instead. Either is accepted.
