# bambino — Lazy connections and API consistency

**Important:** Before starting any phase, read this document in its entirety. Read the `README.md` cover to cover. Understand what this library does and who it's for. Do not apply generic software engineering heuristics without grounding them in the project's actual goals.

**Pre-release:** This library has not been released. All API changes are on the table. Do not preserve backward compatibility for external consumers — only for tests and the CLI within the same crate, and only when the phase specifies it.

**When completing a phase:** Update this PLAN.md marking the phase complete. Update the completed phases summary, strictly including **only** what is necessary to inform clean sessions implementing the next phases which cannot be learned from the code itself. Once summarized, remove the phase from PLAN.md.

## Phases 1–17: Complete

Non-obvious decisions a future session cannot derive from the code alone:

- **`from_mqtt()` does not reseed `sequence_counter`** — `ensure_mqtt()` reseeds from `TimerProvider::now_millis()` on lazy connect to de-correlate independent sessions, but `from_mqtt()` (tests and Embassy) intentionally starts at `INITIAL_SEQUENCE_ID` so injected fixture responses remain predictable.
- **`move_relative()`/`extrude()` warn on unhomed axis, never error** — the policy is warn-and-proceed; the `log::warn!` calls in motion.rs are deliberate, not a placeholder for a future error return.
- **`wait_for_homing()` overrides `command_timeout_secs` to 90s** — homing takes far longer than normal commands; the override is intentional.
- **Clap positional `bool` requires explicit action** — `AmsAction::Dry.rotate` uses `#[arg(action = ArgAction::Set, value_parser = BoolishValueParser::new())]`. Clap defaults `bool` fields to `ArgAction::SetTrue` (flag semantics), which panics for positional args at startup. Any future positional bool in the CLI needs the same treatment.
- **`SecureConnect` is gone; MQTT and FTPS now share one connection shape.** `PrinterClient<MqttRawIO, MqttTls, MqttFactory, Timer, FtpsRawIO, FtpsTls, FtpsFactory>` has two symmetric `TlsConnector`+`RawStreamFactory` trios — MQTT's mandatory (no defaults), FTPS's defaulted to dummy types. `RawStreamFactory<RawIO>` (`src/io/mod.rs`, next to `TlsConnector`) replaces the old FTPS-only `FtpDataStreamFactory`; its method is `dial(&self, host, port)`, not `create_data_stream`. Platform impls: `Tokio/EspIdf/EmbassyRawStreamFactory` (dropped the `Ftp` prefix — they're protocol-neutral). `PrinterClient::new(tls, factory, ip, serial, access_code, model)` takes MQTT's pair directly, mirroring `.with_ftps(tls, factory)`'s shape.
- **`MqttRawIO` needs a `PhantomData` field on `PrinterClient`.** It only appears in where-clause bounds (`MqttTls: TlsConnector<MqttRawIO>`, `MqttFactory: RawStreamFactory<MqttRawIO>`), never directly in a field type (unlike `FtpsRawIO`, which appears directly in the `ftps: Option<BambuFtpsClient<FtpsRawIO, ...>>` field) — Rust's E0392 unused-type-parameter check doesn't count where-clause appearances, so `pub(crate) _mqtt_raw_io: PhantomData<MqttRawIO>` is required and must be threaded through every constructor/builder (`new`, `from_mqtt`, `with_timer`, `with_ftps`).
- **`from_mqtt()` uses `PreConnected` for both the MQTT `Tls` and `Factory` slots.** `PreConnected<IO>` implements `TlsConnector<IO>` as an identity passthrough (`connect` returns `Ok(raw_stream)` unchanged — never actually exercised, since `from_mqtt()` never calls `ensure_mqtt()`'s connect path) and `RawStreamFactory<IO>` as `Err(SocketError::NotConnected)` (genuinely unreachable — `ensure_mqtt()` short-circuits on `self.mqtt.is_some()` before either is called). `DummySecureConnect` is deleted outright (no replacement needed — `PreConnected` covers the same role for both new slots).
- **Connect-timeout is now centralized on `PrinterClient`, not per-connector.** `connect_timeout_secs` (default 10s, `.with_connect_timeout(secs)`) bounds `ensure_mqtt()`/`ensure_ftps()`'s *entire* dial+connect sequence via `race_against_connect_timeout()` (`src/client/mod.rs`), which reuses `race()`/`Raced` (now `pub(crate)` in `src/io/mod.rs`, not `src/mqtt/client.rs`) and its `has_real_clock()` guard (skips the race under `DummyTimer`). For `ensure_ftps()` specifically, "entire sequence" means the raw dial *and* `BambuFtpsClient::connect()`'s full login handshake raced together as one future, not just the TCP dial. This replaced the old per-platform `TokioSecureConnector`/`EspIdfSecureConnector::connect_timeout` (both deleted) and closed a pre-existing gap: FTPS's raw dial had no timeout at all before this. `EspIdfTlsConnector::connect_timeout` (handshake-only, for direct non-`PrinterClient` callers) is untouched and still exists as a separate, lower layer.
- **Camera integration follows the same lazy-connect shape as MQTT/FTPS** (`PLAN.md` former Phase 13) — a third `CameraRawIO`/`CameraTls`/`CameraFactory` trio (type params 8–10, defaulted to `DummyRawIo`/`DummyTls`/`DummyFactory`) plus `ensure_camera()`/`connect_camera()`/`camera_connected()`/`with_camera()`/`with_camera_port()`/`with_camera_max_frame_size()` in `src/client/mod.rs`, and `camera()`/`read_camera_frame()`/`disconnect_camera()`/`attach_camera()` in the new `src/client/camera.rs` (mirrors `storage.rs`'s shape). `ensure_camera()` checks `model.quirks().camera_protocol() == CameraProtocol::BinaryJpeg` **before** checking whether `.with_camera()` was ever called, so an RTSPS model (X1/X2/H2/P2S) gets a clear "wrong protocol" error immediately, never a dial attempt or a "not configured" error.
- **`race`, `Raced`, and `read_chunk` now live in `src/io/mod.rs`** (`pub(crate)`), not `src/mqtt/client.rs` — relocated so `camera/binary.rs` didn't have to reach into a sibling protocol module for transport-agnostic utilities built on `AsyncIo`/`TimerProvider`. `mqtt/client.rs` imports them from `crate::io`; `read_exact_packet`/`FrameReadState` stayed put (genuinely MQTT-specific). `BambuBinaryCameraStream::read_next_frame_with_timer()` (`src/camera/binary.rs`) reuses them via its own resumable `CameraFrameReadState`; the public `read_next_frame()` delegates to it under `DummyTimer` — never give it an independent implementation, since two implementations sharing one `read_state` field is a desync hazard.
- **`read_chunk`'s no-deadline branch (`DummyTimer`) now maps a `0`-byte read to `SocketError::ConnectionReset`**, matching the with-deadline branch — previously it forwarded `stream.read()`'s result unchanged, so a legitimate EOF looked identical to "no bytes yet," and callers' fill-loops (`while *filled < buf.len() { ... }`) would spin forever instead of erroring. Caught by a camera regression test expecting a clean disconnect error; benefits any `DummyTimer`-based caller, including `BambuMqttClient::connect()`'s CONNACK/SUBACK read (not independently re-verified against real hardware for this specific edge case).
- **`door_open()`/`active_fault()` cache raw telemetry, decode on access** (mirrors `last_home_flag`/`last_gcode_state`). `last_door_open: Option<bool>` is set unconditionally from `self.model.quirks().is_door_open(print)` inside `poll_telemetry()`; the *accessor* gates on `has_door_sensor()` and returns `None` on sensorless models (A1/A2/P1) instead of the raw quirks method's `false` — a deliberate divergence from `ModelQuirks::is_door_open`'s own contract, kept only at the cached-accessor layer. `last_print_error: Option<u32>` feeds `active_fault() -> Option<DecodedPrintError>` via `decode_print_error()`; a `0` register and "never observed" both collapse to `None` (unlike `is_all_axes_homed()`, no caller action differs between the two here, so no need to distinguish them). `hms` array caching remains out of scope — `Vec<HmsEntry>` is clone-per-update and there's no concrete need yet for multi-alert state beyond "is there a genuine fault."
- **Phase 15 investigated whether AMS/progress/temperature warrant caching and found the desktop-CLI angle was the wrong test.** `bin/bambino-cli/monitor/dashboard.rs` already solves "show me continuously-updated progress/temp/AMS state" by merging incremental `print.*` JSON deltas into its own `serde_json::Map` — but that's an alloc-heavy, untyped-JSON workaround only available on `std`. It doesn't exist on Embassy/no_std, and no `src/client/*.rs` command currently guards its own behavior on AMS or progress/temp state the way `motion.rs`/`thermal.rs` guard on `last_home_flag`. The real motivating consumer is a future embedded status display or a Home-Assistant-style integration bridge that wants a cheap typed "current state" snapshot without holding a full `TelemetryReport` or reimplementing the JSON-merge trick on a target that can't afford it — same justification as the existing `last_home_flag`/`last_door_open` raw-cache-decode-on-access precedent.
- **Phase 16 implemented the Phase 15 plan.** `PrintProgress` (`src/client/types.rs`) bundles `percent`/`remaining_secs`/`layer_num`/`total_layers` into one `Copy` struct (deliberately not four parallel `Option` fields — those four wire values are always consumed together, unlike `home_flag`/`gcode_state`/`door_open`/`print_error`), cached as `last_progress: PrintProgress` and exposed via `print_progress()`. `bed_temperatures()` (`PrinterClient`) reuses `TelemetryReport::bed_temperatures()`'s exact decode logic — extracted into `pub(crate) fn decode_bed_temperatures()` in `src/types/telemetry/mod.rs`, called from both places — sourced from new `last_bed_temper`/`last_bed_target_temper`/`last_device` caches; `last_device` is populated from `report.device()` (its existing top-level-then-`print.device` fallback), which required `poll_telemetry()` to check `report.device()` in addition to its `report.print`-only logic. AMS/tray state is cached raw (`last_ams: Option<AmsStatusReport>`, `last_vt_tray: Option<VirtualTray>`, `last_vir_slot: Option<Vec<VirtualTray>>`) with no scoped predicates — `ams()`/`vt_tray()`/`vir_slot()` hand back the raw sub-report for the caller to query with `AmsUnit`/`AmsTray`'s existing decode helpers. Nozzle/chamber temperature accessors were deliberately left out of this phase (same pattern as bed, revisit once bed is proven against a real consumer). All new `last_*` fields cache-and-decode via a new `update_telemetry_cache()` helper (extracted out of `poll_telemetry()` to keep its cognitive complexity down) and are threaded through all 5 struct-literal reconstruction sites (`new`, `from_mqtt`, `with_timer`, `with_ftps`, `with_camera`).
- **Nozzle diameter/type were considered for Phase 17 and declined.** Already reachable without any cache: `report.device().and_then(|d| d.nozzle.as_ref())` → `NozzleCollection.info: Vec<NozzleInfo>` (`id`/`diameter: Option<f32>`/`nozzle_type: Option<String>`, IDEX), or the flat `report.print.nozzle_type`/`nozzle_diameter` fields on legacy single-nozzle models. Static hardware descriptor, doesn't change between polls the way temperature does — a `PrinterClient` cache wouldn't add value here.

- **Phase 17 added nozzle/chamber temperature, HMS alerts, fan speeds, print speed, and `wifi_signal` accessors**, all following the same `last_*`-raw-cache/decode-on-access shape, plus migrated three of `dashboard.rs`'s hand-rolled decode paths (nozzle, HMS, fan speed) into the shared library functions — chosen because those three involved real branching/quirk logic worth deduplicating, unlike bed/progress/AMS (Phase 16), which were left as-is in the CLI since there's no logic to delete, only which map is read.
  - **`decode_nozzle_temperatures(device, nozzle_temper, nozzle_target_temper) -> Vec<(u8, u16, u16)>`** (`src/types/telemetry/mod.rs`, `pub`, re-exported at `crate::types`) ports `dashboard.rs`'s previously CLI-only IDEX flat-field routing quirk (on IDEX models with no live `device.extruder.info`, `nozzle_temper` is nozzle 1's actual and `nozzle_target_temper` is nozzle 0's target — each nozzle only gets half its own reading). `PrinterClient::nozzle_temperatures()` sources it from `last_nozzle_temper`/`last_nozzle_target_temper` (new) + `last_device` (Phase 16, already covers `device.extruder`/`device.nozzle`). Needed to be `pub`, not `pub(crate)`, since `bambino-cli` is a separate binary crate depending on the library like any external consumer — `pub(crate)` items are invisible to it.
  - **`chamber_temperature() -> Option<(u16, u16)>`** gates on `ModelQuirks::ignores_chamber_temperature()` (mirrors `door_open()`'s `has_door_sensor()` gate) — `None` on open-frame models regardless of telemetry, `Some((0,0))` pre-observation on chamber-equipped ones.
  - **`hms()`/`active_hms_alerts()`** cache `last_hms: Option<Vec<HmsEntry>>` raw; `active_hms_alerts()` decodes+filters via the pre-existing `decode_hms_alert()`. Turned out `dashboard.rs`'s existing loop already *was* this exact decode+filter (it already called `decode_hms_alert` directly) — there was no CLI-side dedup opportunity here despite the phase plan assuming one; left `dashboard.rs`'s HMS rendering untouched.
  - **`decode_fan_percentage(raw: Option<&str>, uses_percentage: bool) -> Option<u8>`** (`src/quirks/mod.rs`, `pub`, next to `fan_step_to_percentage()`) replaces `dashboard.rs`'s hand-rolled step-vs-percentage branch; `part_cooling_fan_speed()`/`auxiliary_left_fan_speed()`/`chamber_exhaust_fan_speed()`/`heatbreak_fan_speed()` all call it via a private `decode_fan_speed()` helper supplying `self.model.quirks().auxiliary_fan_uses_percentage()`. **`auxiliary_right_fan_speed()`** is a fifth, unrelated accessor — confirmed against `reference/03_mqtt_telemetry.md`/`04_toolhead_thermal_motion.md` that the X2D/P2S secondary fan reports at `device.airduct.parts[id=160].state` as an already-clamped percentage, a different wire location and encoding than the other four (which are 0–15-step strings) — it reads `last_device` directly, no shared decode function, and cannot be unified with the others. None of these five map cleanly onto `FanTarget`, which has no variant for `heatbreak_fan_speed` (not independently controllable) — kept as five separate methods rather than one `FanTarget`-keyed method.
  - **`print_speed()`/`print_speed_magnitude()`** reuse the existing write-side `PrintSpeed` enum via a new `PrintSpeed::from_level(u8) -> Option<Self>` (confirmed `spd_lvl`'s wire values match `set_print_speed()`'s 1–4 exactly) rather than adding a parallel type.
  - **`wifi_signal()`** caches the raw string; **`is_ethernet_active_via_wifi_signal()`** is a cached-equivalent of `PrinterTelemetry::is_ethernet_active_via_wifi_signal()`'s per-report sentinel check (`"-90dBm"`), so it can be consulted between polls the way `is_all_axes_homed()` already is for `home_flag`.
  - `update_telemetry_cache()` (Phase 16) was split into `update_state_cache()`/`update_progress_cache()`/`update_temperature_cache()`/`update_ams_cache()`/`update_fan_cache()`/`update_speed_and_signal_cache()` to keep cognitive complexity down as the number of cached fields grew — any future `last_*` cache addition should extend one of these (or add a new one), not the top-level dispatcher.
  - All ~11 new `last_*` fields threaded through the same 5 struct-literal sites as every prior phase's cache fields (`new`, `from_mqtt`, `with_timer`, `with_ftps`, `with_camera`).
  - Full gate passed: `cargo test` (335+ passed), `cargo clippy --all-targets -- -D warnings` (both with and without `--features cli`), `--no-default-features --features alloc --lib`, `--no-default-features --features embassy --lib`, and `make check-esp-idf` (esp32c6). Two **pre-existing, unrelated** clippy failures were found gated behind `--features cli` (`src/bin/bambino-cli/probe.rs`'s `needless_borrows_for_generic_args`, confirmed present on a clean checkout via `git stash`) — not fixed, out of scope for this phase, flagged for whoever next touches `probe.rs`.
