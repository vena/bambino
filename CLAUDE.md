# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test Commands

```sh
cargo build                                          # Default host build (tokio + rustls)
cargo build --bin bambino-cli --features cli         # Build the CLI binary
cargo test                                           # Run all tests
cargo test --lib                                     # Library tests only
cargo test test_name                                 # Single test by name
cargo build --no-default-features --features alloc --lib  # no_std compatibility check (must pass)
cargo check --no-default-features --features embassy --lib  # embassy target check (must pass)
```

`make check-fast` runs all of the above (build, test, both feature-gate checks, clippy) in one command; `make check-esp-idf [CHIP=esp32c6]` wraps `scripts/check-esp-idf.sh`; `make check-all` runs both. `.github/workflows/ci.yml` and `.github/workflows/esp-idf.yml` mirror the same commands but are dormant: this repo has no GitHub remote yet, so they don't run anywhere. `esp-idf.yml` is path-filtered to only fire when esp-idf-gated files change, and its cost is higher on GitHub-hosted runners than locally — the script's Docker-volume caching doesn't survive GitHub's ephemeral VMs, so every run there pays the full cold-build cost, not just the first.

Every change must compile under both the default `tokio` feature set and the `alloc`, `embassy`, and `no_std` library targets. Run `cargo clippy` as part of the verification gate. The `--lib` flag scopes the no_std check to library code only — the CLI is host-only. Use `#[cfg(not(feature = "std"))]` imports from `alloc` (String, Vec, format!) for no_std paths.


The `embassy` feature is not implied by `alloc` alone (see `Cargo.toml`) — `io/embassy.rs` and any code gated on `#[cfg(feature = "embassy")]` are *not* exercised by the plain no_std/alloc check above, so both commands are required. The `esp-idf` feature target can't be checked with plain `cargo check` — `esp-idf-sys`'s build script needs Python/cmake/ninja/the ESP-IDF SDK, `rust-src` (tier-3 target, `-Z build-std=std,panic_abort`), and for Xtensa chips a forked Rust toolchain. Run `scripts/check-esp-idf.sh [chip]` (default `esp32c6`, RISC-V) — it pulls the matching `espressif/idf-rust` Docker image and runs the check inside it, using named Docker volumes to cache the cargo registry, rustup/`rust-src`, and `target/` across runs (only the first run per chip pays the full from-scratch cost, confirmed ~5.5 min cold). This is **not wired into CI** (there is no CI in this repo) — it's a manual step, so run it yourself before landing changes to `src/io/esp_idf.rs`. **Confirmed passing as of 2026-07-01** against `esp32c6` (`riscv32imac-esp-espidf`) — this is the first time this file has ever actually been compiled; it did not compile as originally written (see git history around that date for the fixes: `usize`-vs-`u32` length args to `esp_idf_svc::sys::read`/`write`, and `esp_tls_cfg`'s cert fields living behind bindgen union accessors — `cfg.__bindgen_anon_N.field`, not flat on the struct). `espressif/idf-rust` ships both Xtensa (`esp32`, `esp32s2`, `esp32s3`) and RISC-V (`esp32c2`, `esp32c3`, `esp32c6`, `esp32h2`) chip tags; there is no `esp32p4` tag yet — P4 (RISC-V) checks would need the `all_latest` image or `IDF_TARGET=esp32p4` against the `esp32c6` image (unverified, since P4's toolchain needs may differ from C6's — spike before relying on it). Xtensa tags (`esp32`/`s2`/`s3`) are also unverified by this script so far — same build-std/rust-src approach is assumed to apply but hasn't been run.

**Mock tests cannot verify wire-level write/read framing — real hardware can.** Confirmed 2026-07-02: `write_command` in `src/ftps/protocol.rs` was changed from one `write_all("cmd\r\n")` call to two separate `write_all` calls (`cmd` then `\r\n`) to avoid a per-command `String` allocation (commit `6385019`). Every test in `tests/ftps_test.rs` passed against the mock FTP server, but the change broke login against real Bambu firmware (confirmed live on a P1S) — the mock reads a stream regardless of how many writes produced it, so it can't distinguish "one write" from "two writes," and this printer's embedded FTP daemon apparently can't reliably reassemble a command split that way. Fixed by combining back into a single write; see `reference/02_ftps.md` §2.3 and the regression test `test_write_command_sends_single_write_call`. This is a narrow failure class, not a blanket "test everything on hardware" rule — most wire-code changes (new fields, parsing fixes, validation, constants, error handling) don't need it. **The narrow class that does: changing the *shape* of writes or reads on an already-working wire path** — splitting one write into several (or merging several into one), changing read granularity (byte-at-a-time vs. buffered), or wrapping a read in new timeout/select/race logic. Changes in this class must be physically verified against real hardware before being considered done — passing `cargo test` alone is not sufficient, since mocks read/write a buffer regardless of how many calls produced it. If you're an agent making a change in this narrow class: don't run that verification yourself even if printer credentials (IP/serial/access code) are present in the conversation or environment — ask the user to run the test manually and report the result back. Never write an access code or serial number into a file in this repository (docs, tests, scratch files, commit messages) — treat them the same as any other credential.

**CLI-only dependencies live behind the `cli` feature, not `tokio`.** `crossterm`, `env_logger`, and any future CLI-exclusive dep (e.g. `clap`) must be gated by `cli = ["dep:...", "tokio"]`, never added to the `tokio` feature directly — see the feature comments in `Cargo.toml` for why. `[[bin]] required-features = ["cli"]` in Cargo.toml enforces this at the target level — every file under `src/bin/bambino-cli/` starts with `#![cfg(feature = "cli")]`.

## Architecture

**bambino** is a multi-platform async Rust crate for controlling Bambu Lab 3D printers over LAN. It compiles to three targets from one codebase: host (tokio/rustls), ESP-IDF (std), and bare-metal (embassy/no_std).

### Key Invariants

1. **No direct platform I/O in library code.** All network I/O goes through abstract traits in `src/io/` (`AsyncIo`, `TlsConnector`, `RawStreamFactory`, `AsyncUdpSocket`, `TimerProvider`). Never use `tokio::` or `std::net::` outside `src/io/`. `TlsConnector` wraps an existing raw stream in TLS; `RawStreamFactory` dials a fresh pre-TLS stream to host:port (used for both MQTT's lazy connect and FTPS's data channel). `TimerProvider::now_millis()` provides monotonic clock for platform-agnostic timeouts.

2. **All model-specific behavior goes through the quirks engine.** Access via `model.quirks()` — never match on `BambuModel` variants for behavioral dispatch. Strategy structs live in `src/quirks/models/`.

3. **MQTT commands follow the Payload+Request pattern** (`src/mqtt/commands.rs`, `src/diagnostics/kprofile.rs`):
   - A `#[derive(Serialize)]` payload struct with typed fields
   - A wrapper struct with a single `pub print: PayloadType` field (or `pushing:`, `system:`, `info:`)
   - An `impl` block with `pub fn new(...)` constructor

### Non-Obvious Type Decisions

- **Temperature fields** are `Option<f64>` — the wire sends both integers (H2D) and floats (P1S/A1). Bed and nozzle targets arrive as separate `_target_temper` fields (never composite-packed). Use `unpack_temperature()` only for `chamber_temper` on models with active chamber heaters, and for `ExtruderInfo.temp` on IDEX platforms.
- **`DeviceTelemetry`** appears at two wire locations (see its doc comment for which triggers which) — check both when reading, don't assume one based on model. `TelemetryReport::device(&self) -> Option<&DeviceTelemetry>` (`src/types/telemetry/mod.rs`) does the fallback for you — checks top-level `device` first, then `print.device` — mirroring `bed_temperatures()`'s existing first-found-wins pattern. Prefer it over manually checking both locations for nozzle/extruder/airduct/ctc/ext_tool sub-telemetry.
- **`PrinterTelemetry::is_ethernet_active()`** implements the *disputed* pybambu `home_flag` bit-18 heuristic (OrcaSlicer maps the same bit to `is_support_prompt_sound`) — not confirmed authoritative. `is_ethernet_active_via_wifi_signal(&self) -> bool` (checks `wifi_signal == "-90dBm"`) is the doc-recommended alternative per `reference/03_mqtt_telemetry.md` `[REF-NET-PORTS]`. Both are kept since neither source is proven correct; consider cross-checking both on unfamiliar firmware.
- **`ExtruderInfo.temp`** uses the same composite packing as `chamber_temper` (values > 500 encode target << 16 | actual). Use `ExtruderInfo::temperatures()` to decode. The `ExtruderCollection.state` bitmask encodes extruder count (low 4 bits) and active index (bits 4–7); use `active_extruder_index()` / `extruder_count()`.
- **`PrinterClient::poll_telemetry()`** returns `TelemetryEvent` (discriminated enum), not raw `MqttMessage`. Use `poll_raw()` or `BambuMqttClient::poll_telemetry()` for raw access. The message buffer lives on `BambuMqttClient` — command-response methods like `get_version()` stash non-matching messages there, and `poll_telemetry()` drains them first.
- **`PrinterClient<MqttRawIO, MqttTls, MqttFactory, Timer, FtpsRawIO, FtpsTls, FtpsFactory>`** is generic over two symmetric `TlsConnector`+`RawStreamFactory` trios — MQTT's (`MqttRawIO`/`MqttTls`/`MqttFactory`, mandatory, no defaults) and FTPS's (`FtpsRawIO`/`FtpsTls`/`FtpsFactory`, defaulted to dummy types) — plus `Timer: TimerProvider`. `SecureConnect` (deleted, pre-1.0, `PLAN.md` Phase 12) used to be MQTT's connection strategy; MQTT now uses the same `TlsConnector`+`RawStreamFactory` shape FTPS always did. `new(tls, factory, ip, serial, access_code, model)` creates a lazy client — MQTT connects on first use via `ensure_mqtt()` (dials via `factory.dial()`, wraps via `tls.connect()`). `from_mqtt(mqtt_client, serial, model)` wraps a pre-connected `BambuMqttClient` using `PreConnected` for both the MQTT `Tls` and `Factory` slots (tests, Embassy) — `PreConnected`'s `RawStreamFactory::dial` is unreachable since `ensure_mqtt()` short-circuits on `self.mqtt.is_some()` first. Consuming builders `.with_timer(timer)` and `.with_ftps(tls, factory)` change type parameters. Non-consuming builders `.with_mqtt_port(port)`, `.with_ftps_port(port)`, and `.with_connect_timeout(secs)` return `Self`. `connect_timeout_secs` (default 10s) bounds `ensure_mqtt()`/`ensure_ftps()`'s combined dial+connect sequence via `race_against_connect_timeout()` (`src/client/mod.rs`), reusing the `race()`/`has_real_clock()` pattern from `src/mqtt/client.rs`. `DummyTimer::now_millis()` returns 0, so the elapsed-time check in `poll_until` never fires — chain `.with_timer()` for real timeouts. `mqtt().await?` and `storage().await?` return `Result`-wrapped mutable refs, auto-connecting if needed. `connect_mqtt()` / `connect_ftps()` for eager connection; `mqtt_connected()` / `ftps_connected()` for status. FTPS config is consumed on first connection via `.take()` — reconnecting requires a new `PrinterClient`.
- **`AmsTray.id`** is `String` (wire sends `"0"`, not `0`). **`CtcInfo.temp`** is `u32` (composite-packed integers, not floats).
- **K-profile priming quirk** (see doc comment on `ExtrusionCaliGetRequest` in `kprofile.rs` for why): `PrinterClient::get_k_profiles()` auto-primes; opt out via `set_k_profile_primed(true)`.
- **`AmsUnit.info`** is `Option<String>` — wire sends hex-encoded bitmask (e.g. `"11002103"`). Parse with `u64::from_str_radix(s, 16)`. Bits 0–3 = AMS type, bits 4–7 = dry_status, bits 8–11 = extruder assignment (0=right, 1=left, 0xE=uninitialized), bits 22–25 = dry_sub_status.
- **`BedTelemetry`** (`device.bed`) uses the same composite packing as `chamber_temper` — `bed.info.temp` values > 500 encode `(target << 16) | actual`. Present on H2/P2/X2 models; old-gen models use `bed_temper` / `bed_target_temper` instead.
- **`vir_slot`** is separate from `vt_tray` — IDEX models send `vir_slot: Vec<VirtualTray>` (one per extruder), while single-nozzle models send `vt_tray: VirtualTray`. Both use the same `VirtualTray` schema.
- **`BambuBinaryCameraStream::with_max_frame_size(self, max: usize) -> Self`** — non-consuming builder overriding the default 10MB frame-size cap (`CAMERA_FRAME_MAX_SIZE` in `src/camera/binary.rs`), following the same `mut self -> Self` convention as `PrinterClient::with_mqtt_port`/`with_ftps_port`. Embedded (`no_std`/Embassy) callers should lower it to match their actual JPEG resolution/buffer budget — the 10MB default can exceed a bare-metal target's entire SRAM, and an allocation failure there hits the uncatchable `alloc_error_handler` abort, not a `Result`. Also note: `BambuBinaryCameraStream::authenticate()` returning `Ok(())` only confirms the handshake packet was written+flushed — the port-6000 protocol has no ack byte, so a rejected access code surfaces later as a `ConnectionReset` from `read_next_frame()`, indistinguishable from a transient network blip.
- **`camera::rtsps::build_rtsps_url`** returns `Result<String, BambuError>`, not `String` — it validates `access_code` is non-empty ASCII alphanumeric (the documented LAN access code format) before interpolating it into the URL, returning `BambuError::ProtocolViolation` on failure instead of silently building a malformed URL from a copy-paste mistake (stray whitespace/newline). `camera::rtsps::rewrite_rtsp_request_uri` only rewrites the request-line URI text — it does not recompute or repair an already-computed Digest `Authorization` header; see its doc comment.
- **`BambuFtpsClient` poisons itself after a control-channel desync.** `list_directory`/`upload_file`/`download_file` set a private `poisoned: bool` field if an error occurs after the server's `150`/`125` "opening data connection" reply but before the matching final reply (`226`/etc.) is read — that window leaves the control channel mid-response, so a later unrelated command could otherwise silently misread the stale trailing reply as its own. Every public method on the client calls `check_poisoned()` first and returns `BambuError::ProtocolViolation` immediately once the flag is set; there is no un-poisoning. `disconnect()` also sets it unconditionally on the way out (idempotent — a second call is a no-op) and stays `&mut self`/non-consuming by design, since `PrinterClient::storage()` only ever exposes `&mut BambuFtpsClient`. A poisoned client must be discarded — reconnect via a fresh `BambuFtpsClient::connect()` call. `PrinterClient::disconnect_storage()` composes with this: it calls `disconnect()` then resets `self.ftps` to `None`, so `storage()` reconnects cleanly next time instead of handing back a poisoned client.
- **`validate_ftp_path()`** (`src/ftps/protocol.rs`, `pub(crate)`) rejects `\r`/`\n`/NUL in any path argument before it's interpolated into an FTP command line (CR/LF would let a malicious/compromised printer or MITM inject a second command). Called by every path-taking method on `BambuFtpsClient`. `parse_unix_listing` (`src/ftps/parser.rs`) applies the same filter to parsed `FtpFile.name` values, silently skipping entries that fail it, so a filename round-tripped into another FTP command can't do the same.
- **`ModelQuirks::bed_temp_max` takes a `mains_220v: Option<bool>` parameter** (breaking signature change, pre-1.0) — `fn bed_temp_max(&self, mains_220v: Option<bool>) -> u16`. Only `X1CQuirks` uses it: the official spec sheet states the safe bed ceiling is genuinely voltage-dependent — 110°C on a 220V-region unit, 120°C on a 110V-region unit (counterintuitively, *higher* mains voltage gets the *lower* ceiling). `Some(true)` → 110°C, `Some(false)` → 120°C, `None` (no `home_flag` telemetry observed yet) conservatively clamps to 110°C. Every other model ignores the parameter (`_mains_220v: Option<bool>`) and returns its existing flat constant — `X1EQuirks` included, since X1E's chamber-heater bed ceiling isn't voltage-dependent per the spec. `PrinterTelemetry::is_220v_power(&self) -> bool` (`src/types/telemetry/report.rs`) reads `home_flag` bit 3 (`0x00000008`), mirroring `is_door_open_from_home_flag`'s pattern. `PrinterClient::set_bed_temperature` (`src/client/thermal.rs`) computes `mains_220v` from `self.last_home_flag` (the client's cached raw `home_flag`, not a full `PrinterTelemetry`) using the same `POWER_220V_BITMASK` constant, following the existing precedent in `src/client/motion.rs` of client-side code masking `last_home_flag` directly rather than routing through a `PrinterTelemetry` method call.
- **`AsyncUdpSocket` vs `BindableUdpSocket`** (`src/io/mod.rs`): `AsyncUdpSocket` is `send_to`/`recv_from` on an already-existing socket — implemented by every platform, including Embassy. `BindableUdpSocket: AsyncUdpSocket` adds `bind(addr: &str) -> Result<Self, SocketError>` (construct-and-bind-in-one-step) — only implementable where the OS supports dynamic socket creation (tokio, ESP-IDF). `EmbassyUdpSocket` intentionally does **not** implement `BindableUdpSocket`: embassy-net's `UdpSocket::new()` requires pre-allocated buffer slices and its `bind()` takes a typed `IpListenEndpoint`, not a string, so there is no honest way to implement it. Mirrors the `TlsConnector`/`RawStreamFactory` split (see Key Invariant 1). Any function that needs to auto-bind its own sockets (like `discover_devices`) must bound its socket type parameter on `BindableUdpSocket`, not `AsyncUdpSocket` — this makes "call it with an Embassy socket type" a compile error instead of a runtime one.
- **Connect-phase timeouts: two layers, not one.** `PrinterClient::ensure_mqtt()`/`ensure_ftps()` (`src/client/mod.rs`) centrally bound their *entire* dial+TLS-connect sequence via `connect_timeout_secs` (default 10s, `.with_connect_timeout(secs)`), racing the combined future against `self.timer.sleep()` — this is the layer that matters for `PrinterClient` users on every platform, tokio/ESP-IDF/Embassy alike (`PLAN.md` Phase 12; superseded the old per-connector `TokioSecureConnector`/`EspIdfSecureConnector::connect_timeout`, both deleted). Separately, `EspIdfTlsConnector` (`src/io/esp_idf.rs`) still carries its own `connect_timeout: Duration` field (default `DEFAULT_CONNECT_TIMEOUT`, 10s) plus `.with_connect_timeout(d) -> Self`, bounding only its handshake retry loop (tracked via `EspIdfTimer::now_millis()`, same `saturating_sub`-against-a-budget pattern as `poll_until`) — this layer exists for direct (non-`PrinterClient`) consumers of that connector, and returns `SocketError::TimedOut` instead of looping forever on `WouldBlock`. `EmbassyTlsConnector::connect` (`src/io/embassy.rs`) has **no** connector-level equivalent — it has no retry loop of its own to bound (the hang risk lives inside `embedded-tls`'s handshake await), so a direct (non-`PrinterClient`) caller needing a bounded connect must race it against `embassy_time::with_timeout` themselves.
- **ESP-IDF TLS connect errors are mapped, not collapsed.** `EspIdfTlsConnector::connect` (`src/io/esp_idf.rs`) previously mapped every non-WouldBlock handshake failure to `SocketError::ConnectionRefused` regardless of cause. `map_esp_tls_connect_error()` now distinguishes DNS/address failures (`ESP_ERR_ESP_TLS_CANNOT_RESOLVE_HOSTNAME`, `EHOSTUNREACH`/`ENETUNREACH`/`EADDRNOTAVAIL` → `SocketError::AddressNotAvailable`), genuine refusals (`ESP_ERR_ESP_TLS_FAILED_CONNECT_TO_HOST`/`ECONNREFUSED` → `ConnectionRefused`), timeouts (`ESP_ERR_ESP_TLS_CONNECTION_TIMEOUT`/`ETIMEDOUT` → `TimedOut`), and an opaque fallback (`SocketError::Other`, now carrying the formatted `EspError` rather than a fixed string — see next point).
- **`SocketError::Other` is `Cow<'static, str>`, not `&'static str`.** Mirrors `BambuError::ProtocolViolation`'s existing `Cow` usage for the same reason — dynamic message content in a `no_std`+`alloc`-compatible way (`#[cfg(feature = "std")] use std::borrow::Cow` / `#[cfg(all(not(feature = "std"), feature = "alloc"))] use alloc::borrow::Cow`, same split as `error.rs`). `SocketError` is no longer `Copy` as a result (Cow's owned variant isn't). Lets ESP-IDF's error mapping attach the actual `EspError` (`format!("ESP-IDF TLS handshake failed: {err}")`) instead of a fixed compile-time string; every other construction site just wraps a string literal via `.into()`/`Cow::Borrowed`.
- **`TlsConnector::connect` dropped its unused `port: u16` parameter** (breaking, pre-1.0) — signature is now `async fn connect(&self, host: &str, raw_stream: RawStream) -> Result<Self::Stream, SocketError>`. No implementer (tokio/embassy/ESP-IDF) ever read it: the raw stream handed in is already connected to its target port by the time `connect()` is called. `RawStreamFactory::dial(&self, host: &str, port: u16)` (the trait that does the actual port-aware dial) is unaffected — port is exactly what it needs. Test mocks that faked port-dependent behavior (`tests/common/io.rs`'s `FailingDataTlsConnector`, used to simulate a data-channel-only TLS failure) now track "was this the first `connect()` call on this instance" via an `AtomicBool` instead — matches how `BambuFtpsClient` actually sequences connects (control channel once, then one data-channel connect per transfer), and doesn't depend on removed information the trait no longer carries.
- **`PrinterClient::toggle_led` was renamed to `set_led`** (breaking, pre-1.0) — same signature (`node: &str, turn_on: bool`), name-only change for consistency with the `set_*` naming used by every other hardware/thermal setter (`set_fan_speed`, `set_bed_temperature`, `set_airduct_mode`, etc.). `set_fan_speed` (`src/client/hardware.rs`) also gained guard checks for `FanTarget::AuxiliaryLeft`/`FanTarget::ChamberExhaust` against `ModelQuirks::supports_auxiliary_left_fan()`/`has_chamber_exhaust_fan()`, mirroring the pre-existing `FanTarget::AuxiliaryRight`/`supports_auxiliary_right_fan()` guard, plus a `log::warn!` when `speed_percent > 100` before clamping (matching the clamp-warning pattern in `src/client/thermal.rs`).
- **`EspIdfUdpSocket` no longer busy-spins on `recv_from`.** It now holds an `EspIdfTimer` (constructed once in `bind()`) and sleeps `UDP_RECV_POLL_INTERVAL` (15ms) on the `WouldBlock` path before returning `SocketError::TimedOut`, matching `TokioUdpSocket::recv_from`'s 100ms-timeout pacing. Without this, callers polling in a tight loop (e.g. `discover_devices`) turned every empty read into an immediate return, burning 100% CPU for the full discovery window.
- **`BambuMqttClient::poll_wire`/`read_exact_packet` (`src/mqtt/client.rs`) now enforce a per-read deadline against a connection that stalls with zero incoming bytes** — the post-connect half of the "connection can hang forever" problem; `PrinterClient`'s `connect_timeout_secs` (`src/client/mod.rs`, `ensure_mqtt()`/`ensure_ftps()`) only covers the dial+TLS-connect sequence, not a connection that goes silent after being established. `poll_wire<T: TimerProvider>(&mut self, timer: &T)` races each individual low-level read step (one MQTT header/remaining-length byte, or one chunk of payload — never a whole multi-byte `read_exact`) against `timer.sleep(remaining)`, using a hand-rolled `race()` combinator (`pub(crate)`, reused by `race_against_connect_timeout` in `src/client/mod.rs`) built on `core::future::poll_fn`/`core::pin::pin!` rather than `tokio::select!` or `embassy_futures::select` — one code path, no `#[cfg]` branching, works identically on all three targets. **Correctness hinge:** on a timeout, bytes already read for the in-progress frame must never be lost, or the next read desyncs the stream parser permanently (same failure class as the `write_command` regression above). `FrameReadState` (a new field on `BambuMqttClient`) persists exactly this progress across a timed-out `read_exact_packet` call, so a subsequent call resumes mid-frame instead of misreading stale payload bytes as a new header. `connect()`'s own CONNACK/SUBACK reads deliberately do **not** get this protection (out of scope — `io.md` Phase 1's territory) and keep their pre-existing unbounded-read behavior by passing `DummyTimer` explicitly. **`TimerProvider` gained `has_real_clock() -> bool`** (default `true`; `DummyTimer` overrides `false`) specifically to make this safe: `DummyTimer::sleep()` completes instantly regardless of the requested duration (by design, so it never blocks generic retry/backoff loops), so racing a read against it unconditionally would make `poll_wire` fail immediately on *every* call under the default `PrinterClient` configuration instead of providing real protection — `read_exact_packet` checks `has_real_clock()` and falls back to a plain unbounded read when `false`, preserving `DummyTimer`'s exact prior semantics (message-count valve only, no wall-clock protection — same documented tradeoff as `poll_until`). `BambuMqttClient::poll_telemetry()` (public, timer-less) is unaffected — it calls the new `poll_telemetry_with_timer(&DummyTimer)` internally, so direct callers (e.g. `tests/mqtt_test.rs`) keep identical behavior; `PrinterClient::poll_telemetry()`/`poll_raw()` call `poll_telemetry_with_timer(&self.timer)` to get real protection when a real `Timer` is configured. **Requires real-hardware verification** (per the rule below) — not yet done; mocks (`tokio::io::duplex`) can prove the race/resume mechanism is correct but cannot prove real TCP/TLS behaves the same way under an actual stalled connection.
- **Camera integration lives on `PrinterClient`** (`PLAN.md` Phase 13) — a third `CameraRawIO`/`CameraTls`/`CameraFactory` trio (type params 8–10, defaulted to `DummyRawIo`/`DummyTls`/`DummyFactory`, same shape as the FTPS trio) is forward-looking/consistency-driven, not bug-driven: there's no known camera-specific TLS quirk today. `ensure_camera()` (`src/client/mod.rs`) checks `model.quirks().camera_protocol() == CameraProtocol::BinaryJpeg` **before** checking whether `.with_camera()` was ever called — an RTSPS model (X1/X2/H2/P2S) gets "this model doesn't support this connection type" immediately, never "you forgot to configure it," and never dials. `.with_camera(tls, factory)` (consuming builder) / `.with_camera_port(port)` / `.with_camera_max_frame_size(bytes)` (non-consuming) mirror the FTPS builders exactly. `camera()`/`read_camera_frame()`/`disconnect_camera()`/`attach_camera()` live in the new `src/client/camera.rs`, mirroring `storage.rs`'s shape; `ensure_camera()`/`connect_camera()`/`camera_connected()`/the builders live in `client/mod.rs` alongside `ensure_mqtt()`/`ensure_ftps()`. `disconnect_camera()` exists for the same reason `disconnect_storage()` does: once `camera_config` is consumed, a dead stream would otherwise leave `self.camera` stuck `Some(...)` forever behind `ensure_camera()`'s `is_some()` short-circuit.
- **`race`, `Raced`, and `read_chunk` moved from `src/mqtt/client.rs` to `src/io/mod.rs`** (as `pub(crate)`, alongside `AsyncIo`/`TimerProvider` which they're built on) so `camera/binary.rs` doesn't have to reach into a sibling protocol module for transport-agnostic utilities — `mqtt/client.rs` now imports them from `crate::io` instead of defining them; `read_exact_packet`/`FrameReadState` stayed put (genuinely MQTT-specific). `BambuBinaryCameraStream::read_next_frame_with_timer()` (`src/camera/binary.rs`) reuses them for the same per-read-deadline purpose, with its own resumable `CameraFrameReadState` (an extra `ReadingHeader{filled}` variant MQTT's state machine doesn't need, since MQTT's 1-byte header can't partially complete a single `read()` the way camera's 16-byte header can). The public `read_next_frame()` delegates to `read_next_frame_with_timer(..., &DummyTimer, ...)` — do not give it an independent implementation; two implementations sharing one `read_state` field is a desync hazard.
- **`read_chunk`'s no-deadline branch (`DummyTimer`, `has_real_clock() == false`) now maps a `0`-byte read to `SocketError::ConnectionReset`, matching the with-deadline branch.** Found while implementing Phase 13: the branch previously just forwarded `stream.read(buf).await`'s result unchanged, so a legitimate EOF (`Ok(0)`, peer closed the connection) looked identical to "no bytes yet, keep looping" to callers like `read_exact_packet`/`read_next_frame_with_timer`, whose fill-loops (`while *filled < buf.len() { ... }`) would then spin forever re-reading zero bytes instead of erroring — caught by a new camera regression test expecting a clean disconnect error after the mock server's frame count was exhausted. This is a general correctness fix in a function only just centralized into `io/mod.rs` by this same phase, not a scope-expanding change; `BambuMqttClient::connect()`'s CONNACK/SUBACK read (which passes `DummyTimer` explicitly) benefits from the same fix but wasn't independently re-verified against real hardware for this specific edge case.

## Key Conventions

- `serde_json` is used with `default-features = false` — always use `serde_json::to_vec` (not `to_string`) for payloads.
- Library code uses the `log` crate facade (`log::debug!`, `log::trace!`, `log::warn!`) — never `println!`.
- `BambuError` has dual `Display` impls: `thiserror` under `std`, manual under `no_std` (kept in sync by `test_display_consistency`). `ProtocolViolation` uses `Cow<'static, str>`.
- Magic numbers are extracted into named `pub(crate) const` blocks in each module. Use existing constants rather than introducing new literals.
- All MQTT sequence IDs and task IDs must be clamped to 32-bit signed integer max (`TASK_ID_MAX`). Use `clamp_task_id()` for task IDs.
- Protocol specs live in `reference/` as numbered markdown files. Always verify field names and types against reference docs when adding or modifying commands. When external sources (pybambu, Bambuddy, Bambu Studio, wire captures) contradict a reference doc, update the reference doc with the correction and note the verification source.
- Use MODEL_MATRIX.csv to track physical characteristics of printer models. When new information is **confirmed** about a printer model, update MODEL_MATRIX.csv
- When adding public types, modules, traits, or changing conventions, update this file. Keep it concise — document constraints and gotchas, not API summaries.
- **PLAN.md phases must be self-contained.** Each phase must be implementable by a clean session with zero prior conversation context beyond the existing codebase. When adding or altering a phase, inform the next session of what we learned and guide it by spelling out: the problem being solved (not just what to build), design constraints and trade-offs that shape the implementation, ordering dependencies between items, and which items are trivially independent. If a task has a hard design decision, state the options and either pick one or mark it as "decide first." A phase that requires reading git history or guessing at intent is underspecified.
